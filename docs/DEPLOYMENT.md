# Почему проект разворачивается локально в Docker, а не в облаке (Firebase и аналогичные)

Решение: весь стек (PostgreSQL, API, сайт, языковая модель) запускается одной командой `docker compose up` на сервере,
которым владеет архив или его подрядчик, в том числе в центре обработки данных на территории Республики Казахстан.
Управляемые облачные платформы (Firebase, Supabase, Vercel, облачные LLM API) не используются.

## 1. Требования к размещению данных

Сайт Государственного архива ВКО хранит персональные данные: учётные записи сотрудников и посетителей (e-mail, имя,
журнал действий), избранное и подписки посетителей. Кроме того, это информационная система государственного органа.

## 2. Что из этого следует для архитектуры

- **Данные остаются там, где их разместит заказчик.** База, файлы (`backend/storage`), поисковый индекс и журнал действий лежат в томах Docker
  на одном сервере. Переезд на другой сервер или в казахстанский ЦОД — это перенос трёх томов и файла `.env`, а не переписывание проекта.
- **Облачная платформа привязала бы проект к поставщику.** Firebase означает Firestore и Firebase Auth вместо PostgreSQL и собственной
  модели ролей, а данные физически находились бы в регионе поставщика. Если окажется, что размещение за пределами РК недопустимо, пришлось бы
  переписывать слой данных, авторизацию и права доступа (`authorize`), а не просто сменить хостинг.
- **Стек переносим.** PostgreSQL 16 (pgvector, pg_trgm), FastAPI, Next.js и Ollama работают в любом дата-центре, у любого казахстанского
  хостинг-провайдера или на собственном оборудовании архива, в том числе без доступа в интернет (после загрузки образов и моделей).
- **ИИ работает локально.** Запросы посетителей и тексты документов обрабатывает модель Ollama внутри контура (`OLLAMA_URL`), поэтому
  они не передаются зарубежному поставщику. Облачный LLM API означал бы трансграничную передачу каждого запроса.
- **Закрытые документы не покидают контур.** Права проверяет сервер, файлы отдаются только через API (`/api/files/{id}`), а в облачное
  хранилище с публичными ссылками они не попадают.

## 3. Что мы получаем и чем платим

| | Локальный Docker | Облачная платформа |
|---|---|---|
| Место хранения данных | Выбирает заказчик (ЦОД в РК) | Регион поставщика |
| Перенос на другой сервер | Тома и `.env` | Переписывание слоя данных и авторизации |
| Работа без внешних сервисов | Да, кроме необязательного входа через Google | Нет |
| Первый запуск | `docker compose up`, модель ИИ скачивается один раз (несколько ГБ) | Быстрее: готовая инфраструктура |
| Эксплуатация | Бэкапы, обновления, мониторинг на стороне владельца сервера | На стороне поставщика |

Главная цена локального варианта — эксплуатация: владелец сервера сам делает резервные копии (`make backup`), обновляет образы и следит за
диском. Для демонстрации это снимается командой `docker compose up`, для продуктивной среды нужны регламент резервного копирования
и мониторинг (см. `docs/OPEN_ISSUES.md`).

## 4. Внешние зависимости, которые остаются

| Зависимость | Когда используется | Как отключить |
|---|---|---|
| Тайлы карты OpenStreetMap | Карты филиалов и «Историческая карта» (браузер посетителя запрашивает плитки) | Развернуть собственный тайловый сервер и заменить URL в `frontend/src/components/map/branch-map.tsx` |
| Google Identity Services | Только если задан `GOOGLE_CLIENT_ID`: бэкенд проверяет ID-токен у Google | Оставить `GOOGLE_CLIENT_ID` пустым (по умолчанию кнопка скрыта) |
| Загрузка моделей Ollama и образов Docker | Первый запуск | Предзагрузить в закрытый реестр |

Остальное работает без исходящих подключений: поиск, ИИ-помощник, OCR (Tesseract), переводы (готовый файл `backend/seed/translations.json`).
